# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

SOCRATES ("Suite Of Community RAdiative Transfer codes based on Edwards and Slingo") is a
Fortran radiative-transfer code for planetary atmospheres, originally developed and maintained
by the UK Met Office. This is the FormingWorlds fork
(`github.com/FormingWorlds/SOCRATES`), which adds Python/Julia tooling and serves as the
radiative-transfer core of the PROTEUS framework (called from the atmosphere model AGNI). The
codebase is Fortran-first with Python and Julia layers built on top of the compiled binaries.

## Build

```bash
./configure          # generates make/Mk_cmd (compiler, netCDF paths, precision) via nf-config/gfortran
./build_code          # stages src/ into bin/, runs mkdep, builds via make/Makefile
. ./set_rad_env        # must be sourced after building, before running any tools/tests
```

- `configure` requires `nf-config` (netCDF-Fortran) and `gfortran` on `PATH`; it writes
  `make/Mk_cmd` (compiler flags, netCDF include/lib paths, precision) from scratch each run and
  deletes `bin/`, `set_rad_env`, and a few generated `sbin/` binaries first. Precision defaults
  to double; `./configure single` builds single precision (`-freal-8-real-4`).
- `build_code` copies sources from many `src/<subpackage>/` directories plus `make/*` into a flat
  `bin/` staging directory (only copying newer files), regenerates dependencies (`bin/mkdep`),
  then runs `make` there. `bin/` and `sbin/` build products are gitignored — never edit files
  under `bin/` directly, edit the corresponding file under `src/` or `make/` and rebuild.
- Machine/compiler presets (copy a matching `set_prog_env_<preset>` and `Mk_cmd_<preset>` into
  `bin/` and force a clean rebuild if they differ from what's there):
  `./build_code azure_gfortran12`, `./build_code azure_ifort19`, `./build_code monsoon3_gfortran12`,
  `./build_code ash_ifx2025`. Without a recognized preset, `build_code` falls back to
  `set_prog_env_<hostname>` if present, otherwise plain `configure`-generated `Mk_cmd`.
  Untested/undocumented other presets exist under `make/Mk_cmd_*` (e.g. `arc4`, `dali`, `cazld`,
  `MAC_APPLESILICON`) for specific clusters — read `build_code` before assuming one works.
- The final argument to `build_code` (after a preset, if any) is passed straight through as a
  `make` target inside `bin/`, e.g. `./build_code cdl`, `./build_code cdf`,
  `./build_code l_run_cdf`, or `./build_code azure_gfortran12 cdl`. With no target it uses the
  Makefile's default (`all`).
- `sbin/` contains small C utilities (`Cinc_field`, `Cscale_field`, `Cgen_null`) that
  need their own compile: `cd sbin && make`. `build_code` does this automatically.
- After any build, `RAD_DIR`, `RAD_BIN`, `RAD_SCRIPT`, `RAD_DATA` and `PATH`/`MANPATH`/`PYTHONPATH`
  come from sourcing `. ./set_rad_env` (itself generated by `configure`, gitignored, and
  hardcoded to the absolute repo path — regenerate it if the repo is moved/cloned elsewhere).
- Always build from the repository root via `./build_code`; don't try to compile directly inside
  `src/` — the Makefile only exists (as generated `Mk_*` includes) inside `bin/` after staging.
- Build failures around netCDF include/lib paths are almost always a `configure`/`Mk_cmd`
  environment problem (missing or wrong `nf-config` on `PATH`), not a source-code issue — re-run
  `./configure` after fixing the environment rather than editing `Mk_cmd` by hand.

## Tests

```bash
cd examples && ./quick_tests   # fast regression set, exercises multiple sbin/ drivers
cd examples && ./slow_tests    # fuller/slower regression set
```

Individual cases live under `examples/<case>/` (e.g. `netcdf/CIRC_case6`, `7460_28`,
`aer_cmp`, `corr_k`, `runes`, `runes_nc`, `raw_input`) and are run directly, e.g.:

```bash
cd examples/netcdf/CIRC_case6 && ./run_me
cd examples/netcdf/CIRC_case6 && ./run_me_sph   # pseudo-spherical geometry variant
cd examples/corr_k && ./run_me
```

Tests require a completed build and a sourced `set_rad_env`; they compare output against
reference data checked into each case directory.

## Lint

CI lints Fortran via [Fortitude](https://github.com/PlasmaFAIR/fortitude) on every PR
(`.github/workflows/lint-fortran.yaml`, using the shared `MetOffice/growss` workflow), with
rules selected in `.fortitude.toml`. Run locally with `fortitude check .` if installed.

## Architecture

### Fortran core (`src/`, `make/`)

Source is split into subpackages under `src/`, each with a distinct role:

- `general`, `modules_gen`, `modules_core`, `aux` — shared utilities, constants, common types
- `radiance_core` — the core two-stream/spherical-harmonic radiative transfer engine and the
  eight `Str*` derived types that make up the public interface (see below)
- `correlated_k` — correlated-k gas absorption coefficient generation
- `scatter` — Mie scattering calculations for aerosol/cloud optical properties
- `illumination`, `interface_core`, `nlte` — solar illumination geometry, driver interfaces, non-LTE
- `cosp_control`, `cosp_github/` — optional COSP satellite simulator coupling
- `flexchem`, `odepack` — optional chemistry coupling

`make/Makefile` builds several static libraries (`radlib`, `cklib`, `scatlib`, `cosplib`,
`flexchemlib`) from these subpackages, then links many executables described by the
`Mk_target_*` include files. Compiler/link flags come from the generated `Mk_cmd`; per-subpackage
source lists come from `Mk_src_*`/`Mk_mod_*`; dependency ordering is auto-generated into
`Mk_depend`/`Mk_depend_cdf` by `bin/mkdep`.

### Calling interface

All arguments to the core routine `radiance_calc` are grouped into eight Fortran derived types
defined in `src/radiance_core/def_*.F90`: `control`, `dimen`, `spectrum`, `atm`, `cld`, `aer`,
`bound` (all `INTENT(IN)`) and `radout` (`INTENT(OUT)`). A calling model sets up `control` and
`spectrum` once, then per timestep/segment allocates and populates `dimen`/`atm`/`cld`/`aer`/
`bound` before calling `radiance_calc`. See `docs/Explanations/interface.md` for the full call
sequence. This same set of types is what the Julia bindings wrap (below).

### Command-line entry points (`sbin/`, `man/`)

`sbin/` scripts (`Cl_run_cdf`, `Cl_run_cdl`, `Ccorr_k`, `Cscatter`, `Ccdf2cdl`, `Cinterp`, etc.)
are the user-facing CLI wrappers around the executables built into `bin/`; they manage temporary
files and expected option handling. `man/man1/*.1` are the authoritative reference for each
script's options (`man Cl_run_cdf`, etc., once `set_rad_env` has updated `MANPATH`). Prefer
these wrappers over invoking `bin/` executables directly when scripting.

### Julia bindings (`julia/`)

`julia/gen/*` and the compiled `julia/lib/*.so`/`*.o`/`*.mod` are **generated and gitignored** —
do not hand-edit files there (only `julia/src/` and `julia/lib/Makefile` are tracked in git).
`julia/src/generate_wrappers.jl` parses the `Str*` derived types out of
`src/radiance_core/def_*.F90` (via `ParseFortran.jl`) and emits matching `ISO_C_BINDING` Fortran
wrappers (`julia/gen/*_C.f90`) plus Julia wrapper modules (`julia/gen/*_JL.jl`), which are
assembled into the hand-maintained `julia/src/SOCRATES.jl`. `julia/lib/Makefile` compiles the
generated Fortran against the already-built `bin/radlib.a` (via `RAD_DIR`) into
`libSOCRATES_C.so`. Regenerating these is only needed when the `Str*` type definitions change
(e.g. when adding a gas) — see below.

### Python layers

- `python/` — standalone analysis/post-processing scripts (e.g. `ncplot.py`, `ncprofiles.py`,
  `RFMIP_run_soc.py`, `cloud_optics.py`); not a package, invoked as scripts, expect `RAD_DIR`/
  `PYTHONPATH` from `set_rad_env`. Dependencies in `python/requirements.txt`.
- `spectraltools/` — a **separate**, not-originally-Met-Office Python toolkit (own
  `spectraltools/README.md`, own license) for building SOCRATES SpectralFiles from line-list
  cross-section/opacity databases. See "spectraltools workflow" below.

### `spectraltools/` workflow

Purpose: computing correlated-k coefficients directly from a line-list is expensive, so this
toolkit splits the work into (1) generating high-resolution absorption cross-sections from a
line-list/database, independent of SOCRATES, and (2) feeding those cross-sections through the
compiled SOCRATES correlated-k/scattering tools to bin them into a spectral file. It supports
DACE, ExoMol/ExoCross, and HITRAN/HITRAN-CIA as cross-section sources, plus MT_CKD H2O and an
optional UV cross-section set.

Setup and layout (`spectraltools/src/utils.py` enforces this at import time — it raises
immediately if `RAD_DIR` is unset or `spectraltools/output/` doesn't exist):

- Requires a compiled SOCRATES with `. ./set_rad_env` sourced (so `RAD_DIR` is set and `Ccorr_k`/
  `Cscatter_average`/`prep_spec` are on `PATH`), plus `dace-query`, `h5py`, `netCDF4`,
  `matplotlib`, `numpy`, `requests`.
- Input cross-sections go under `spectraltools/data/<db>/<absorber>/` (e.g. `data/dace/H2O/`,
  `data/hitran/CO2/`), CIA pair files under `data/cia/`, and optional UV cross-sections under
  `spectraltools/moleculesUV/`. Everything under `data/` and `output/` is gitignored — the user
  must create (or symlink) `output/` themselves before running anything.
- Module layering: per-source readers `src/dace.py` / `src/exocross.py` / `src/exomol.py` /
  `src/hitran.py` each know how to locate and parse that database's file format; they all
  produce the common `xsec` cross-section container defined in `src/cross.py`. `src/ptf.py`
  dispatches by source name and finds, for a requested pressure/temperature, the closest
  available cross-section file. `src/netcdf.py` packs mapped cross-sections into the common
  netCDF grid format SOCRATES expects. `src/spectral.py` is the layer that actually drives the
  compiled SOCRATES binaries (see below). `src/phys.py` holds physical constants and the
  formula/isotopologue naming lookups (`chemsafe`, `iso_to_formula`) shared across sources.

Typical pipeline, in order (the `T*.py` scripts are meant to be run from inside `spectraltools/`
with `set_rad_env` sourced; `Tinterpolate_dace.py` and `Tmake_spectralfile.py` are "wizard"
scripts — edit the parameters at the top of the file, then run with no arguments):

1. `Tdownload_cia.py` — download the needed HITRAN CIA pair files (e.g. `H2-H2`, `CO2-CO2`, ...)
   into `data/cia/`.
2. `Tinterpolate_dace.py` — for a chosen isotopologue/line-list (via the `dace-query` API),
   interpolate line-by-line cross-sections onto a target pressure/temperature grid and write raw
   DACE binary files into `data/dace/<formula>/`. (Only needed for the DACE source; ExoCross and
   HITRAN cross-sections are obtained externally per each tool's own docs.)
3. `Tconvert_dace.py <formula>` — read the raw `.bin` files back out of `data/dace/<formula>/`
   and consolidate them into a single netCDF file in `output/` (mainly useful as a standalone
   sanity check/export step; `Tmake_spectralfile.py` does its own netCDF packing internally).
4. `Tmake_spectralfile.py` — the main driver. For a configured `source`, gas list (`vols`),
   `alias`, pressure/temperature grids, band count/selection `method`, and wavenumber
   range/resolution (`numin`/`numax`/`dnu`), it:
   1. validates gas names and checks each has data at `data/<source>/<gas>/`;
   2. clears any stale `output/<alias>_*` files from a previous run of the same alias (keeps
      pre-built netCDFs if `preNC=True`);
   3. checks each gas's cross-section data actually covers the requested p/t/wavenumber domain;
   4. picks band edges (`spectral.best_bands`) and writes the spectral-file "skeleton" plus the
      P–T grid files SOCRATES will read (`spectral.create_skeleton`);
   5. for each gas, maps every target (p, t) to its closest source cross-section file
      (`ptf.map_ptf`, logged to a CSV) and packs the result into `output/<alias>_<gas>.nc`;
   6. shells out to the compiled **`Ccorr_k`** (line-by-line k-coefficients per gas via
      `spectral.calc_kcoeff_lbl`, and CIA k-coefficients per gas pair via
      `spectral.calc_kcoeff_cia`) — each call is written to a `<alias>_*.sh` script under
      `output/` and run with `subprocess.run(["bash", ...])` so the exact invocation is logged;
   7. if `drops` is set and `H2O` is among the gases, shells out to **`Cscatter_average`**
      (`spectral.calc_waterdroplets`, using `data/cloud/scatter_drop_type5`) to fit water droplet
      optical properties;
   8. assembles everything into the final `output/<alias>.sf` spectral file by driving the
      compiled **`prep_spec`** tool with a generated input script (`spectral.assemble`), then
      checks the result for `NaN` values.
5. `Tplot_absorption.py <absorber> <source> <pressure> <temperature> <yunits> ...` — spot-check a
   single cross-section (nearest available p,t file) by plotting it.
6. `Tcalc_checksum.py <path>` — BLAKE2b checksum of a file, e.g. to verify a distributed spectral
   file's integrity.
7. `Tclean_output.py <alias> [options]` — delete intermediate `output/<alias>_*` files for a run
   (keeps the "real" per-gas/CIA/water-droplet netCDFs unless told to remove them too).

`Ccorr_k`, `Cscatter_average`, and `prep_spec` are the same compiled SOCRATES tools documented in
[Command-line entry points](#command-line-entry-points-sbin-man) above — `spectraltools` is a
Python driver around them, not an independent implementation.

### Documentation (`docs/`)

Built with `zensical`/mkdocs (`mkdocs.yml`, structured per the Diataxis framework: Tutorials,
How-to guides, Explanations, Reference) and deployed by `.github/workflows/docs.yaml`. The

directory's `lx` script and pulled into the site as PDFs) are the authoritative source for
the physics and interface — `docs/Explanations/interface.md` is a condensed summary of the
technical guide.

## Adding a new gas

This is a manual, cross-language, multi-file change — no code generation covers it end to end.
Per `README.md`, search for an existing similarly-integrated gas (e.g. `ho2no2`) across the repo
and mirror its additions; always append new gases to the *end* of existing lists. Expect to edit
at least:

- `src/interface_core/socrates_set_spectrum.F90`
- `src/modules_gen/input_head_pcf.f90`
- `src/modules_gen/refract_re_ccf.f90`
- `src/radiance_core/def_control.F90`
- `src/radiance_core/gas_list_pcf.F90`
- `julia/src/SOCRATES_C.f90`
- `julia/src/SOCRATES.jl`
- `spectraltools/src/phys.py`
- `spectraltools/src/utils.py`

Avoid the "lazy" Fortran pattern of bulk-filling remaining array elements — `generate_wrappers.jl`
parses the source textually and needs explicit, individual assignments to work.

## Repository conventions

- `set_rad_env`, `bin/`, `sbin/Cgen_null`, `sbin/Cinc_field`, `sbin/Cscale_field`, `make/Mk_cmd`,
  `julia/gen/`, `julia/lib/*.so`, and `spectraltools/{data,output}/` are all generated/local and
  gitignored — never hand-edit or commit into them.
- `version` is a single line (e.g. `2603.8`) read by `configure` and stamped into generated
  Julia wrapper headers.
- `.github/CODEOWNERS`: repo-wide owner is `@mo-jmanners` (Met Office); `src/cosp_control` and
  `src/cosp_github` are separately owned by `@Petzi1`.
